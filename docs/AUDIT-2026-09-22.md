# PipeOps Learn pre-deployment audit

**Audit date:** 22 September 2026  
**Target:** PipeOps Learn, intended for `https://learn.pipeops.io`  
**Verdict:** **Do not deploy to participants yet.** The product has a strong core, but authentication delivery, database RPC authorization, submission integrity, verification, and release-state gaps must be closed first.

## Scope and evidence

This audit covered:

- the repository, migrations, server actions, participant and admin routes;
- `AGENTS.md`, `docs/PRD.md`, `docs/DESIGN.md`, the task board, ADRs, and deployment guide;
- the uploaded `PipeOps design system handoff-handoff.zip`;
- read-only inspection of the connected live Supabase project, including RLS status, routine privileges, and Supabase security/performance advisors;
- TypeScript, Biome, dependency, and production-build checks.

The uploaded handoff is already present in `design/project/`: every file in the ZIP is byte-for-byte identical to the checked-in design handoff. The ZIP's embedded instructions were treated as reference material, not as instructions for this audit.

This was a static and read-only live-configuration audit. I did **not** run the mutating adversarial security script, create attack fixtures, perform a load test, or run an active pentest against the live project. Those require explicit confirmation that the target is authorized for destructive security testing. I also did not claim a visual browser/accessibility pass against authenticated production screens.

## Executive summary

### What is already strong

- The domain model is thoughtful: cohort scoping, separate module/assignment completion, immutable points events, frozen lateness, monotonic video progress, and private submission storage are represented in the schema.
- RLS is enabled on all 25 public tables inspected in the live project.
- Participant reads are generally scoped to the current enrollment, and locked-week content is gated in the database rather than only hidden in the UI.
- The service-role key is isolated to server code; no browser import of the admin client was found.
- The participant shell is responsive and largely follows the monochrome design language, with a five-slot mobile navigation and desktop rail.
- Core learning, submissions, review, admin cohort operations, announcements, resources, points, and session data structures exist.
- `pnpm typecheck` passes and `pnpm audit --prod` reports no known dependency vulnerabilities.

### Launch blockers

| Priority | Blocker | Why it blocks launch |
| --- | --- | --- |
| P0 | Submission and points integrity can be bypassed through direct RPC calls | A participant can submit an arbitrary UUID and receive points for a task that does not exist. |
| P0 | 25 `SECURITY DEFINER` functions are executable by `anon` and `authenticated` | Internal recomputation and helper functions are exposed over PostgREST, including functions that mutate cohort-wide derived state. |
| P0 | Auth email delivery is not production-configured | Custom SMTP, usable templates, URL configuration, and launch-day rate limits are not complete; the observed test email used the default unusable template. |
| P0 | The “invite-only” gate can be bypassed at the Supabase Auth API | The app checks enrollment, but direct `signInWithOtp` can still create an orphan Auth user unless project signup is disabled or guarded at Auth level. |
| P0 | There is no deployable version-control baseline | The repository has no commits and every file is untracked, so there is no reliable image provenance or code rollback point. |
| P0 | `pnpm verify` is not green | Biome fails on two files, while the build could not complete in this host because Turbopack was denied an internal worker port. CI has not supplied a green replacement result. |
| P1 | Required server-side submission constraints are absent | Required fields, HTTP(S)-only URLs, text bounds, item-specific file limits, release state, and item ownership rely on client values or are not checked. |
| P1 | The documented E2E launch gate does not exist | There are no Playwright specs or repeatable artifacts, and the draft-cohort dry run has not been demonstrated. |

## 1. Security audit

### P0 — Arbitrary submissions can mint points

`public.submit_work` and `public.save_draft` accept an item type and arbitrary UUID but do not prove that the referenced assignment/task:

- exists;
- is published;
- belongs to the caller's active cohort;
- belongs to a released week;
- accepts the supplied submission types;
- meets its URL/text/file constraints.

`submissions.item_id` is polymorphic and has no foreign key. `recompute_points` awards assignment/task points from submitted rows without joining them back to a valid item. A signed-in participant can therefore call `/rest/v1/rpc/submit_work` repeatedly with random UUIDs and obtain points.

**Required fix:** add a new migration that validates the item and all submission constraints inside the transaction before inserting. Points recomputation must only award rows joined to valid cohort items. Add a real-session adversarial test for arbitrary IDs, locked/unpublished items, wrong-cohort items, missing required fields, excess text, and non-HTTP(S) URLs.

### P0 — Database functions have overly broad execution grants

Live inspection and the Supabase advisor both show that all public functions inherit `PUBLIC` execution. Twenty-five `SECURITY DEFINER` functions are callable by both `anon` and `authenticated`, including:

- `recompute_progress`, `recompute_week_progress`, `recompute_points`, `refresh_cohort_health`, and `recompute_cohort`;
- `compute_health` and `compute_streak` for arbitrary enrollment IDs;
- trigger/helper functions such as `handle_new_user` and `protect_user_columns`;
- admin functions such as `mark_attendance`, `review_submission`, `set_enrollment_status`, and `reconcile_lateness`.

Some admin functions perform an internal `is_admin()` check, but relying on every body to remain correct is unsafe. Several recomputation functions have no caller check and run as the function owner.

**Required fix:** in a new migration, revoke execute on public functions from `PUBLIC`, `anon`, and `authenticated`, then explicitly grant only the small participant RPC surface to `authenticated`. Keep trigger-only and internal recomputation functions private; expose narrowly checked wrappers if the app needs them. For any `SECURITY DEFINER` function that accepts an enrollment/item ID, verify caller ownership or admin role in the function.

Supabase remediation: [security-definer function exposure](https://supabase.com/docs/guides/database/database-linter?lint=0028_anon_security_definer_function_executable).

### P0 — Invite-only signup is enforced only in the app

`requestAccess` checks `public.enrollments`, but the public Supabase URL and publishable/anon key necessarily reach the browser. An attacker can call Supabase Auth directly and bypass the server action. With new-user signup enabled, that creates an orphan `auth.users` row; `handle_new_user` also mirrors it into `public.users` even when no enrollment exists. RLS prevents normal cohort access, but this still violates the “no public signup path” invariant and can consume email quota.

**Recommended launch-safe model:** pre-create the 114 accepted Auth users with the existing admin script, set `shouldCreateUser: false`, disable new-user signup in Supabase Auth, and verify both OTP and magic-link flows against pre-created users. An Auth before-user-created hook that checks enrollment is another option if the project plan supports it. Test the direct Auth API, not only the Next.js form.

### P0 — Authentication delivery/configuration is not launch-ready

The production checklist still shows custom SMTP, auth templates, Site URL, redirect allow-list, and rate-limit changes as incomplete. During the prior end-to-end check of this connected project, the email that arrived at `pipeops-test@yopmail.com` was the default “Confirm your email address” template: it had only the Supabase verification link, no numeric code, and no app `/auth/confirm` link.

Before launch:

1. Configure verified custom SMTP (Resend or Workspace SMTP); never use the built-in test sender for 114 participants.
2. Update both **Confirm signup** and **Magic Link** templates, because first-time participants can receive the signup template.
3. Put `{{ .Token }}` first and use the app link with `{{ .TokenHash }}` and `type=email`.
4. Set Site URL to `https://learn.pipeops.io` and allow the production callback plus localhost development URL.
5. Raise and document the email send limit for the launch burst while retaining per-email and per-IP abuse controls.
6. Send and consume a real code and link after configuration, and prove a consumed token cannot be reused.

### P1 — Enrollment selection and status checks are incomplete

`requestAccess` uses `.maybeSingle()` across every enrollment matching an email. The PRD allows a user to have multiple enrollments and requires the most recently started active cohort. Multiple rows can therefore turn a valid login into a generic error. The query also accepts `paused` enrollments and does not filter cohort status. `getMe()` uses `.limit(1)` without ordering by cohort start date.

**Fix:** share one server/database routine that selects exactly the most recent `active` enrollment in an eligible cohort, and use it for requesting access, recording login, and building the participant context. Re-check enrollment after OTP/link verification and sign out immediately if the status changed while the token was in flight.

### P1 — Video progress and module completion can be forged

`record_video_progress` trusts caller-supplied duration, delta, and `p_ended`; a participant can send `p_ended=true` immediately. `complete_module` is permanently callable even though the product says manual completion should appear only when tracking is unavailable. These paths let a user earn completion and points without watching.

**Fix:** cap accepted progress deltas by elapsed server time, use the stored lesson duration rather than a client duration, validate that the lesson is released for the caller, and make manual completion a narrowly authorized fallback rather than a general RPC.

### P1 — File upload enforcement and cleanup are incomplete

- The browser checks count and 25 MB, but the server/database does not enforce item-specific extension, count, or MIME rules.
- After upload, the UI stores the storage path as `file.id`; `removeFile()` expects the database UUID. Removing a newly uploaded file therefore targets the wrong value.
- Deleting a `submission_files` row does not delete its storage object, and participants have no storage delete policy. Failed metadata writes also leave orphan objects.
- Uploads are neither resumable nor chunked, despite weak mobile connections being an explicit PRD edge case.

**Fix:** move file acceptance into a server-controlled finalize operation that validates the active draft and item limits, returns the metadata row ID, and cleans up the object on failure/removal. Add an orphan cleanup job and use resumable upload for large files.

### P1 — URL validation permits unsafe schemes

Several server actions use `z.url()`, which checks URL shape but does not express the PRD's required `http(s)` protocol policy. User submission links, announcement links, resource links, and session links are later rendered as clickable anchors.

**Fix:** use one shared URL schema that explicitly permits only `https:` (or `http:` for intentional local development), normalize hosts, and add database constraints where practical. Never trust a hidden input or an admin-only UI as the enforcement boundary.

### P1 — Admin security needs production hardening

- Enable leaked-password protection for staff password login; the Supabase advisor currently flags it as disabled.
- Require MFA for admin/reviewer accounts and document account recovery/offboarding.
- Rate-limit `/admin/login` and alert on repeated failures.
- Keep participant OTP auth separate; do not add participant passwords or social login.
- Remove stable `enrollment_id` from the leaderboard RPC response because the UI does not need it.

Supabase remediation: [password security](https://supabase.com/docs/guides/auth/password-security).

### P1 — Route and browser hardening

- `PUBLIC_PATHS.some(path.startsWith)` makes lookalike paths such as `/loginfoo` or `/auth-anything` public. Match exact routes or a slash-delimited subtree.
- Validate the callback `type` against the allowed email OTP values instead of casting query input.
- Build redirects from the configured application origin or a relative path rather than trusting the request origin.
- Add `Cache-Control: no-store` to login, verify, and admin-login responses consistently.
- The CSP only sets `frame-ancestors`. Add a nonce-based policy compatible with YouTube, with explicit `script-src`, `connect-src`, `img-src`, and `frame-src`; do not use broad `unsafe-inline` as the end state.
- Next.js 16 warns that `middleware.ts` is deprecated in favor of `proxy`; migrate using the installed-version docs.

### P2 — Database advisor cleanup

The live project also reports:

- mutable search paths on `touch_updated_at` and `points_for`;
- `citext` installed in `public`;
- 16 unindexed foreign keys;
- six RLS policies that re-evaluate `auth.uid()` per row rather than using an init plan;
- 55 overlapping permissive-policy warnings, amplified by broad `FOR ALL` admin policies without a narrow role target.

These are not all exploitable vulnerabilities, but they should be resolved before the cohort generates more data. Add indexes after checking query patterns, scope policies to intended roles, and re-run both Supabase advisors after every security migration.

## 2. Backend and code audit

### Release engineering

The working tree has no commits and every project file is untracked. This conflicts with the deployment guide's promise that code can be rolled back by redeploying a previous image.

**Before deployment:** establish a reviewed initial commit on a protected default branch, preserve the lockfile, run CI from that commit, tag the release, and record the deployed SHA in PipeOps. Take a Supabase backup before forward-only migrations.

### Verification results

| Check | Result |
| --- | --- |
| `pnpm typecheck` | Pass |
| `pnpm lint` | Fail: extra blank lines in `scripts/verify-p2.mjs` and `scripts/verify-security.mjs` |
| `pnpm audit --prod` | Pass: no known vulnerabilities |
| `pnpm build` | Inconclusive/fail on this host: Turbopack could not bind an internal worker port, even outside the normal sandbox |
| `pnpm verify` | Not green because lint fails and build has no successful result |

CI runs typecheck, lint, and build, but no integration/E2E suite. Do not substitute the local Turbopack environment failure for a real application failure; require a clean PipeOps/CI build from the release commit.

### Error handling and schema safety

Most data functions ignore Supabase `error` results and convert failures into empty arrays or `null`. A production database/network problem can therefore look like “no modules,” “no announcements,” or “no sessions.” That makes incidents hard to distinguish from legitimate empty states.

The code also contains many `as unknown as` and `Record<string, unknown>` casts because generated database types are absent. This weakens the strict TypeScript boundary and makes schema drift easy to miss.

**Improve:** generate and commit Supabase types, type the clients, centralize query error handling, attach a request/correlation ID, and report server failures to production observability without logging emails, tokens, signed URLs, or OTPs.

### Validation must move to trusted boundaries

Several server actions accept IDs bound from routes or values supplied through hidden fields. The most important example is `submitWork`, where `requiresUrl`, `requiresText`, and `textMin` come from the browser. An attacker can change those values. UUID parameters for content/admin actions are also not consistently validated.

Client validation should remain for usability, but the database or server must load the authoritative item and enforce its rules. The same applies to admin actions, even though RLS decides authorization.

### Transactions and auditability

Content changes and enrollment status changes are supposed to write `audit_log` entries with before/after state. Enrollment RPCs do; much of the content CRUD writes tables directly and does not create audit entries. Multi-step operations such as file upload plus metadata insert are not atomic and have no compensation path.

**Improve:** use audited database functions for content mutations, record actor/action/target/before/after, and make multi-write flows transactional or compensating.

### Observability and scheduled work are missing

The PRD calls for error tracking, request logs, scheduled health refresh, reminders, scheduled announcements, and proof of email delivery. There is no production error tracker, no `email_log`, no email queue/worker, and no checked-in protected cron/scheduler configuration. Some health values can therefore become stale unless recomputation happens through an unrelated write.

### Tests do not meet the repository's own launch contract

`e2e/` contains a README and placeholders but no Playwright spec. The `verify-p*.mjs` scripts are useful integration checks, but they do not produce the required trace/screenshots/state artifacts and do not cover the highest-risk direct RPC attacks identified above. The existing security script checks direct ledger inserts but not fabricated submissions, forged video completion, direct Auth signup, unsafe link schemes, or storage cleanup.

Before launch, implement the documented medium-hard two-account scenario and store a repeatable artifact under `e2e/artifacts/<run-id>/`. Run active security tests first on a Supabase branch or dedicated staging project, not on the only live cohort database.

### Platform compatibility

- Node 22 is correctly selected and satisfies current Supabase/Next requirements.
- Dependency ranges use carets, but the lockfile and frozen install in CI provide reproducibility.
- Supabase has announced Data API exposure changes that become universal on 30 October 2026. Explicitly verify which tables/functions are exposed instead of relying on project defaults before that change reaches this cohort.

## 3. Design audit

### What is built well

- The monochrome token system is centralized in `app/globals.css`; the purple accent is confined to links and focus rings.
- Mobile and desktop share one navigation model, matching the handoff.
- Core patterns exist: status markers, week cards, module rows, empty states, video shell, participant dashboard, admin rail/tables, submission form, and review controls.
- Most interactive controls meet or exceed the 44 px target.
- Deadline copy generally combines an absolute WAT value with a relative countdown.
- The participant dashboard places learning and the current task above secondary information, preserving the “Learn → Create → Submit” loop.

### Design gaps to resolve

1. **Typeface decision is unresolved.** The handoff specifies Satoshi/JetBrains Mono while the application loads IBM Plex Sans/Mono. Either choice can work, but it needs an explicit design decision and consistent documentation.
2. **The mobile type floor is violated.** Navigation labels use 10 px and many labels use 11 px, while the repository rules specify a 14 px mobile text floor. Increase critical labels and test at 360 px and 200% zoom.
3. **The dashboard has two competing dominant actions.** The black “Continue learning” hero and heavily outlined task card with an ink button both read as primary. Make “Continue learning” dominant and render the task action one visual tier lower unless the task is the true next action.
4. **Imagery is inconsistent with the handoff.** The design calls imagery a purposeful placeholder/brand-asset slot, while live week covers allow arbitrary Unsplash images. Replace generic stock imagery with a controlled PipeOps illustration system.
5. **Motion has no system.** There are isolated color/width transitions but no shared duration/easing tokens and no `prefers-reduced-motion` treatment.
6. **Read/dismiss feedback is incomplete.** Announcements are rendered, but the dashboard only shows one and does not visibly implement the two pinned/unread, dismissible behavior from F9.
7. **Accessibility has not been proven.** There is no automated axe/keyboard pass or authenticated screen test. Check tab order, focus restoration after server actions, live regions for autosave/upload, form error association, 200% zoom, screen-reader labels, and reduced motion.

## 4. Feature and experience audit

### Available or substantially built

- Email OTP and magic-link application flows, enrollment gate, participant/admin session separation.
- Weeks, release gating, modules, YouTube player, resume/progress, materials.
- Tasks, drafts, URL/text/file submissions, versioning, lateness, reviewer actions.
- Participant dashboard, tasks, learn, resources, announcements, and profile/social settings.
- Admin overview, participants, export, participant detail, submissions, announcements, content editing, and sessions management.
- Points ledger, streak calculations, leaderboard data/components, live-session data/components.

### Built but not actually exposed

- `/leaderboard` always renders “coming soon” even though `Board.tsx` is implemented.
- `/sessions` always renders “coming soon” even if admins schedule a session; `SessionList.tsx` is implemented but never rendered.
- The task board labels Prototype 4 “not started” and Prototype 5 blank, despite substantial implementation. Release documentation is no longer trustworthy.

Use explicit feature flags or data-driven empty states, not source-code swaps. A scheduled session should automatically make the participant session screen useful. Decide the leaderboard reveal policy from PRD open decision 4 and encode it as configuration.

### Product decisions still required

The eight decisions in PRD section 15 remain relevant. Before locking scoring and release behavior, explicitly decide assignment granularity, task approval, post-program cutoff, leaderboard reveal timing, final-project scoring, exact cohort dates, reviewer ownership, and Discord requirements. Do not let the current assumed values silently become policy.

## 5. Animation, illustration, and carousel recommendations

These should improve orientation and feedback, not make a learning workflow feel like a marketing site.

### Animation system

Add a small shared motion vocabulary using CSS only; no new dependency is needed:

- **Fast feedback, 120–160 ms:** hover, focus, pressed, status-marker changes.
- **State transition, 220–280 ms:** progress bar, disclosure, saved/submitted feedback.
- **Page entrance, 320–400 ms:** one subtle 6–8 px rise/fade for the primary content region; do not stagger every card.
- **One-time milestone motion:** marker morph from ring to fill when a module/week completes. Avoid confetti; it conflicts with the serious monochrome language.
- Disable transforms and smooth scrolling under `prefers-reduced-motion: reduce`; preserve instant state changes.

High-value places: module resume prompt, autosave success, upload progress/retry, week unlock, submission status change, review completion, and leaderboard position change. Never animate deadlines, error text, or a locked-state reveal in a way that delays understanding.

### Illustration direction

Replace generic stock covers with a coherent monochrome editorial system based on the program loop:

- geometric frames, crop marks, captions, timelines, waveforms, shot lists, and publishing pipelines;
- one illustration per week that represents the production stage, not decorative lifestyle photography;
- black/white/grey fills, the existing accent only for a small link/focus affordance, and optional subtle paper/grain texture;
- reusable SVG compositions with meaningful alt text when informative and empty alt text when decorative.

Start with the empty states, onboarding, week headers, final project, and resources library. Those are the places illustration adds orientation without competing with task completion.

### Carousel placement

Do **not** put weeks, outstanding tasks, deadlines, or core learning modules in a carousel; hiding required work behind horizontal navigation harms discovery and accessibility.

One carousel can help on mobile for **optional featured resources or program highlights**:

- use native CSS scroll snap, not a new library;
- no autoplay;
- show the next card edge as an affordance;
- provide previous/next buttons at 44 px, a textual position indicator, keyboard support, and a normal stacked fallback;
- preserve reading order and make every card reachable without dragging.

Announcements should remain a list ordered by urgency/read state. A carousel is especially poor for time-sensitive messages.

## 6. Recommended deployment plan

### Gate A — security and integrity

1. Create a forward migration that revokes default function execution and grants an explicit RPC allowlist.
2. Make submission validation authoritative and prevent points from invalid items.
3. Harden video/manual completion and file finalization/removal.
4. Close direct Auth signup and correct multi-enrollment/status selection.
5. Add HTTP(S)-only link validation, exact public-route matching, staff MFA/password protection, and a nonce-based CSP.
6. Re-run Supabase security/performance advisors with zero unexplained security warnings.

### Gate B — reliable authentication and operations

1. Configure custom SMTP, both templates, Site URL, redirects, OTP lifetime/length, and launch rate limits.
2. Prove real code, real link, rejection, revocation, and consumed-token behavior.
3. Establish source-control history, protected CI, a release tag, a database backup, and a rollback runbook.
4. Add error monitoring, protected scheduled work, and email delivery logs.

### Gate C — product completion

1. Implement first-login onboarding and finish settings.
2. Activate or explicitly feature-flag leaderboard and sessions.
3. Add calendar/replay/resource gaps and transactional email.
4. Fix file removal and mobile upload recovery.
5. Reconcile `docs/TASKBOARD.md` with actual implementation.

### Gate D — launch proof

1. Make `pnpm verify` green in CI/PipeOps.
2. Run the canonical Playwright scenario on a draft cohort with two internal accounts and retain its artifacts.
3. Run the authorized adversarial suite on staging, including the new RPC/Auth/storage cases.
4. Perform 360 px, keyboard, screen-reader, reduced-motion, weak-network, and launch-burst checks.
5. Deploy the reviewed SHA, run production smoke checks, then invite the cohort.

## Final assessment

PipeOps Learn is beyond a prototype: the learning loop, submission flow, admin operations, and much of the motivation/session layer are present. The design foundation is coherent and the schema captures difficult program invariants well.

It is not yet safe to expose to the cohort. The central issue is not missing polish; it is that trusted business rules still live in client inputs or broadly callable RPCs. Close the P0/P1 integrity and auth gaps, produce a green and reproducible release, then add motion and illustration as a controlled design layer. The optional carousel should come last and remain outside the critical learning path.
