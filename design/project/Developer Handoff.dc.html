02

State machines

WEEK · COMPUTED, NEVER FLIPPED
locked
now < release_at
current
release_at ≤ now < next.release_at
open
now ≥ next.release_at · never re-locks
Locked weeks expose number, title and release_at only, enforced in the query layer. Moving release_at earlier is the "release now" mechanism.
SUBMISSION
draft → submitted
submitted → under_review
under_review → approved
under_review → needs_revision
needs_revision → submitted (v+1)
is_late is a boolean, not a status — computed at submit time and frozen on that version. No rejection state in V1. Resubmission is off once approved.
HEALTH · DERIVED, NEVER EDITED
Active≤ 3 DAYS
Needs attention4–6 DAYS
At risk7D+ OR 2 MISSED
Dormant14D+ / NEVER
Recomputed on every activity write, plus a daily job at 06:00 WAT for people whose only change is time passing. V1 sends no automatic at-risk email.

Progress & scoring

FIXED DENOMINATOR · COHORT 01
Modules12
Required course assignments12
Required programme tasks6
Total required items30
Programme completion % = completed ÷ 30. The denominator never moves, so the number only rises and is comparable between participants.
A week is complete when all modules are complete, all required assignments submitted, and the required task submitted. Module completion and assignment completion are tracked separately and never conflated.
POINTS LEDGER · IDEMPOTENT
MODULE_COMPLETED+10
ASSIGNMENT_SUBMITTED+15
TASK_SUBMITTED+20
ON_TIME_BONUS+5
WEEK_MODULES_BONUS+10
WEEK_COMPLETED_BONUS+10
SESSION_ATTENDED+5
FINAL_PROJECT_APPROVED+30
Theoretical max≈ 660
Unique on (enrollment, rule, target) so recomputation never double-awards. Reversals write a compensating negative row with reversal_of — rows are never deleted. Missing a deadline costs the bonus, never points.
VIDEO & STREAK
Persist position every 15s while playing, and on pause, tab-hide and unload. Debounced.
Track max_position_seconds and watched_seconds separately; % derives from watched_seconds.
Watched at ≥ 90% or on ENDED. Writes are monotonic — a lower position never reduces stored maxima.
VIDEO_PROGRESS events at most once per module per 60s; the authoritative position lives in video_progress.
Streak = unbroken run of qualifying weeks ending at the current week. Unreleased weeks can't break it; an unqualified current week doesn't break it, it just isn't counted yet. A missed week resets to 0.
recompute(enrollment_id) rebuilds week_progress, enrollment rollups and missing points events. Idempotent, safe in bulk — the escape hatch for any live-cohort scoring bug.

ROW-LEVEL SECURITY
01A participant reads content only for cohorts they're enrolled in, and only weeks where release_at ≤ now().
02Read/write only their own submissions and progress; read-only on their own points and activity.
03Leaderboard reads go through a view exposing display name, points, streak and rank — never submissions or emails.
04Admin and reviewer bypass cohort scoping for reads, and are the only roles that write content, reviews, attendance and announcements.
05Points and activity events are never writable by a participant client — they're written server-side from the action that caused them.

06

Open decisions

Assignments per module or per week?
These screens assume 12 — one per module. Per-week (6) changes the fixed denominator to 24.
AFFECTS PHASES 3–6
Does a task need approval to score?
Assumed: submission scores, approval is a quality signal — except the final project (+30 on approval).
When do submissions close?
Assumed: ends_on + 7 days, then read-only. Needs a designed "programme closed" state if you choose a hard cutoff.
Leaderboard from day one?
Assumed: visible immediately with a designed empty state ("first module completed takes #1").
Final project: pass/fail or rubric?
Assumed: approval plus a feedback note. A rubric adds a scoring UI to the review queue.
How many reviewers, and do they own slices?
The queue as designed is unassigned and oldest-first. Per-reviewer ownership adds an assignment column and a filter.
Confirm Cohort 01 dates
Week 1 releases Mon 21 Sep 2026, Sunday 23:59 WAT deadlines throughout.
Is Discord membership verified or just linked?
Designed as a link out. Verification would add an OAuth dependency V1 explicitly avoids.
